# 履歴の種類と選手の記録

履歴の識別子は、データセットや提供元とは独立して管理します。`/categories` エントリーポイントの `HISTORY_TYPES` は46個の **排他ではないタグ** と、それぞれに必要な根拠を定義します。[categories.ja.md](categories.ja.md) を見てください。準備状況は実装上の根拠要件を示し、実データベースに何件あるかを意味しません。1件の事実は1つの `recordId` に一度だけ保存し、複数のタグを付けられます。

提供元の稼働状況と、利用者がデータを選ぶ操作も独立しています。更新が止まった提供元でも、過去のデータが有用なことがあります。原資料、スナップショット、対象期間、出所、利用条件を保存します。利用者はアーカイブを消さずに、提供元や記録の種類を含めたり除外したりできます。再利用権が不明なデータは公開できません。

## 選手の履歴

選手フィードは、変化する通算値ひとつではなく、個別の達成を時系列で保持します。各出来事を選手の安定した識別子と、関係するチーム、大会、シーズン、試合、以前の記録保持者に結び付けます。表示名だけで人物を同一視しません。記録を破られた選手の過去の達成も残します。

たとえば、確認済みの通算得点記録には `career-stat-milestone` と `sport-record` の両方を付けます。その後に別の選手が更新したら、以前の出来事と両選手に結び付く新しい達成記録を追加します。以前の達成を上書きしません。同じ出来事の記念日は元の出来事を参照し、新たな達成として作りません。

ここにある例はデータモデルの説明であり、検証済みの初期データではありません。グレツキー、オベチキン、ルミューの記録をこの文書で事実として主張していません。

## 統計の範囲

統計上の節目や記録には、次の項目を明示します。

- 指標。得点、アシスト、ポイント、パワープレー得点、ショートハンド得点など。
- 大会区分。レギュラーシーズン、プレーオフ、明示的に合算した値、または別の大会区分。区分不明を合算扱いにしません。
- 期間。通算、シーズン、ポストシーズン大会、シリーズ、試合など。
- 対象範囲。大会、リーグ、チーム、ポジション、種目、性別区分、年齢区分、階級など。
- 値、単位、基準値、比較方法。大きい値と小さい値のどちらを記録とするか、同値をどう扱うか。
- 日付の精度、入力データの範囲、達成日を特定する根拠。

レギュラーシーズンとプレーオフの合算値を作るには、定義が一致し、入力が重複せず、全件揃っている必要があります。合算値は独立した統計範囲であり、当然に公式記録となるわけではありません。率や平均を足したり、移籍選手の合計行と各チームの内訳を重複計上したりしません。

シーズン合計からシーズン成績は確認できても、記録値に到達した試合や得点までは特定できません。シーズンの決勝得点数から特定試合の決勝ゴールを決めた選手を推定できません。誕生日、達成年齢、デビュー、引退は別の出来事として扱います。

野球も同じ構造を使い、本塁打、安打、奪三振、盗塁、勝利数、セーブなどの指標を区別します。レギュラーシーズンとポストシーズン、通算とシーズン、リーグと球団の範囲、指標の定義を明記します。率の記録には規定到達条件を残します。現在のデータベースにこれらの入力があるとは仮定しません。

## 記録の更新履歴

取り込み時には、安定した記録定義と各達成イベントを別々に保持します。

| 項目 | 意味 |
| --- | --- |
| `recordDefinitionId` | 指標、対象、大会区分、期間、条件を定める安定 ID |
| `achievementId` | この達成イベントの安定 ID |
| `holderIds` | 検証済みの選手またはチーム。複数の場合もある |
| `action` | 樹立、同値、更新、承認、訂正、取消 |
| `value` / `unit` | 単位と精度が明示された比較可能な結果 |
| `achievedOn` | 実際の達成日と日付精度 |
| `announcedOn` / `ratifiedOn` | 判明している場合の発表日・承認日 |
| `previousAchievementIds` | 同じ条件の以前の達成イベント。共同保持者も含む |
| `supersedesAchievementIds` | 訂正対象。監査履歴は維持する |
| `authority` / `recognitionStatus` | 認定団体と暫定・承認済み・係争中・取消済みの状態 |
| `sourceEvidence` | すべての出典スナップショットと項目 ID |
| `derivation` | 版管理した計算規則、入力 ID、対象範囲、入力ハッシュ |

これらは予定する取り込みモデルであり、現在の公開 `MeigenRecord` が保証する項目ではありません。詳細モデルを公開するときは、版を上げて検証を加えます。追加の根拠や精度を黙って捨てません。

イベント ID を翻訳後の文章、提供元の行番号、変化する通算値から作りません。同じ出来事を複数提供元が裏付ける場合は、引用元をすべて残しながら重複を除きます。記録樹立と後日の承認は、同じ達成に関する別日付の履歴として保持できます。訂正や取消では元のアーカイブを消さず、認定状態と採用可否を更新します。

## 世界記録と競技記録

可能な限り、認定団体と日付のある根拠を使います。世界記録、五輪記録、国内記録、リーグ記録、球団記録、大会記録では対象範囲が異なります。不完全な取り込みデータ内の最大値は、アーカイブ内最高値に過ぎず、自動的に世界記録とは言えません。

比較条件が重要です。陸上の風速、屋内・屋外、手動・電動計時、水泳コース長、用具規則、階級、障害区分などを保存します。条件不明の場合は記録と断定せず、確認が必要です。

古い記録一覧も過去時点のスナップショットとして有用です。後続データが十分でなければ、古い一覧の保持者を現保持者と記しません。提供元の稼働状況、記録の認定状態、現保持者かどうかは別々の属性です。

## 更新と確認

新しい入力が届いたら毎月手動で再計算し、年に一度全履歴を監査する想定です。訂正や遡及投入があれば、該当する選手、大会、記録の全範囲を再計算します。直近の1か月だけを追加すると、古いデータの修正を取り逃します。定期実行の仕組みは作っていません。

注目度や編集上の採用判断は、確認可能な別の人手評価として管理します。通算値の大きさ、有名人であること、自動検出された基準到達だけで、著名性、公式記録、利用許諾が成立するわけではありません。正確な日付の根拠がない出来事は、日付フィードに載せません。年や月しか判明していないときに1月1日を補いません。
